# P-ENG 消息总线评估（Message Bus Assessment）

> 任务：T08 · 自主 owner 队列 · 2026-09-25
> 结论：**维持现状（无集中消息总线）；列出可触发引入的明确条件。**
> 性质：纯评估文档，不引入新依赖、不写新代码、不碰生产。

---

## 1. 现状盘点（实测，非假设）

本系统**不存在**任何集中式消息总线 / 事件代理（无 `event_bus` / `publish` / `subscribe` / `broker` 抽象，grep 全仓 `*.py` 零命中）。
组件间通信由四类**既有的、去中心化**机制承担：

| 机制 | 载体 | 用途 | 耦合度 |
|------|------|------|--------|
| **共享 SQLite（集成介质）** | `data/events.db`(SSoT) | 采集→预测→叙事→评估全链路通过表读写衔接；单写者 `gq/db.py` | 松（DB 即契约） |
| **HTTP REST** | `bridge_service.py :9000` | 前端 / 外部查询唯一入口；80 业务端点 | 中（前端强依赖 bridge） |
| **WebSocket** | `gq/ws_collector.py` | 乐鱼实时赔率 ingestion 单向推送 | 低（采集自闭环） |
| **文件黑板** | `data/collab_journal.jsonl` | 双 AI 协作（Observation/Execution）任务认领 | 松（轮询） |
| **线程推送** | `pipeline/notifiers/{wecom,telegram,wx}_notifier.py` | 告警/信号 → 企业微信/Telegram/微信，`threading.Thread(daemon=True)` 即发即弃 | 最低（fire-and-forget） |

**判定**：当前架构是"数据库即集成介质 + 单 hub REST"的经典单机私有形态，与 §9 技术栈（单机、SQLite WAL、单 owner）自洽。

---

## 2. 维持现状的理由（为何不引入总线）

1. **运维面最小**：单人 owner 系统，每多一个常驻进程 = 多一个需守护/排障/在断电后恢复的点。消息代理（Redis/RabbitMQ/NATS）会增加 SPOF 与重启复杂度，与"自主无人值守、最小存活面"目标冲突。
2. **SSoT 已承担集成职责**：`events.db` 本身就是跨组件的事实源与隐式事件流（新行/状态变更即信号）。再叠一层总线 = 双重事实源，制造一致性负担。
3. **通信图是扇入而非扇出**：当前主要是"采集→DB→预测→DB→前端"的线性流，消费者少（前端 1 个、定时脚本若干）。没有需要一对多实时广播的高频事件。
4. **引入收益不明**：在单机、单进程 bridge 形态下，进程内 `asyncio` 事件循环即可覆盖绝大多数"事件触发"需求，无需外部代理。

---

## 3. 真实存在的缺口（≠ 需要总线，但须记录）

- **推送不可靠且静默**：notifier 为 daemon 线程即发即弃，无重试/背压/投递确认。实证——企业微信推送自 2026-09-18 起因 `errcode 850003`（机器人权限过期）持续失败，**静默丢弃**，无人知会。这是**通知可靠性**问题，不是总线问题。
- **结算事件无确定传播**：一场完赛 → 触发叙事记录 + 校准评估 + 前端刷新，三者各自轮询 DB，无"已结算"事件扇出；若轮询窗口错位，前端可能短暂陈旧。
- **黑板轮询延迟**：`collab_journal.jsonl` 双 AI 协作靠轮询，非即时事件。

> 这些缺口的优先级低于 IR-32 守卫覆盖修复（见 T06 报告）与验证台样本累积（T10/T11），**不应为"上总线"而行动**。

---

## 4. 触发引入总线/事件层的条件（满足任一即重启评估）

以下条件按"最小可行"原则分级——优先进程内方案，最后才上外部代理。

| # | 触发条件（可观测、可量化） | 建议最小方案 | 升级到外部代理的条件 |
|---|--------------------------|------------|-------------------|
| C1 | 推送失败需**持久重试/投递保障**（如 wecom 850003 类静默丢失造成业务中断） | bridge 内"出站队列表"+ 定时重发（仍 SQLite，零新进程） | 仅当多进程并发写推送队列表造成锁竞争 |
| C2 | 同一领域事件消费者 ≥ 3 且需**确定时序传播**（如结算→叙事/校准/前端 必须原子扇出） | bridge 内 `asyncio` 事件路由器（in-process） | 仅当 bridge 需横向拆分多进程 |
| C3 | 系统由单机变**多机/多实例**（bus factor 或吞吐驱动） | — | 直接上 Redis pub/sub（已单机则不必） |
| C4 | 模型治理需**持久化审计流**（walkforward 门禁结果→晋升链不可丢） | 沿用 `collab_journal` / 新增 audit 表（DB 即日志） | 同 C3 |

**铁律约束**：任何总线/事件层方案须满足
- 不增加需人工守护的常驻进程（除非 C3 触发）；
- 不引入跨庄共识通道（IR-32 永久禁令，事件 topic 命名须通过 `tests/test_no_crossbook.py` 守卫）；
- 不触碰 events.db 写入语义（事件流可落独立库 / 新表，但不得改变 SSoT 契约）。

---

## 5. 结论与下一步

- **结论**：维持现状。当前"SQLite SSoT + 单 hub REST + 线程推送"对单机私有、单 owner 系统是最优解；引入总线净增运维负担而无对应收益。
- **优先修的真实缺口**：C1 类推送静默丢失（wecom 850003）——这是诚实红线（IR-30）相关风险，建议作为独立安全任务排期（写出站队列表 + 失败重发 + 状态可见），**不依赖任何总线**。
- **重新评估时点**：满足 C1–C4 任一且量化收益 > 运维成本时，由 owner 决策引入；首选进程内方案。

*本文档为评估结论，不落地任何代码。如需推进 C1 推送可靠性，另开任务。*
